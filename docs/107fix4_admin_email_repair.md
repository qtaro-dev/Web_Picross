# チケット107fix4：架空メールで作成された既存ユーザーのメールアドレス修復機能

## 背景

チケット107 / 107fix系により、ユーザー本人がユーザーデータ画面からメールアドレス変更申請できる機能を実装済み。

しかし、本番テスト中に以下の問題を確認した。

- 初期テスト用に `test@test.com` や `test1@test.com` などの架空メールアドレスで作成したユーザーが存在する
- そのユーザー本人でログインし、ユーザーデータ画面から有効なGmailエイリアスへメール変更申請を行った
- Gmailにはメールが届く場合がある
- しかしVercel Logsでは、Supabase側で以下のようなエラーが出ていた

```text
Supabaseユーザーのメールアドレス変更に失敗しました:
メールアドレス「test1@test.com」は無効です
code: EMAIL_CHANGE_SEND_FAILED
```

このため、`email_change_request_logs` にもログが残らず、画面上も失敗扱いになる。

これは107fix3のログ保存処理だけの問題ではなく、**既存のAuth email自体が架空・無効なテストメールになっているユーザーを、本人の通常メール変更フローだけで修復しようとしていること**が原因。

今後のテストや運用のため、管理者が壊れた/不適切なメールアドレスを持つ既存ユーザーを、安全に修復できる機能が必要。

## 目的

管理者ページから、既存ユーザーのメールアドレスを管理者権限で修復できるようにする。

この修復は、通常の「本人によるメールアドレス変更申請」とは別導線とし、以下を同時に整合させる。

- Supabase Auth側の email
- `profiles.email`
- 管理者ページに表示されるメールアドレス
- ログイン/再設定メール/メール変更申請に使われるメールアドレス

## 対象ファイル（推定）

- `api/admin-update-auth-email.js`
- `api/_adminGuard.js`
- `js/admin.js`
- `js/actions.js`
- `js/render.js`

既存の `api/admin-update-auth-email.js` が存在する場合は、新規作成ではなく、そのAPIを安全に活用・修正すること。

## 実装内容

### 1. 管理者専用のメール修復導線を追加する

管理者ページのユーザー詳細に、管理者専用のメール修復UIを追加する。

表示例：

```text
管理者メール修復
現在のメールアドレス: test1@test.com
修復後メールアドレス: [入力欄]
[管理者メール修復を実行]
```

既存の通常ユーザー向けメール変更申請とは明確に分けること。

### 2. 通常の本人メール変更フローとは別扱いにする

本人のユーザーデータ画面から行うメール変更申請は、引き続きチケット107 / 107fix系の仕様を維持する。

このチケットで追加するのは、以下のようなケースを救済するための管理者修復機能。

```text
初期テストデータのメールが架空
現在メールがSupabase側で無効扱い
本人フローで変更確認メールを送れない
Auth email と profiles.email がズレている可能性がある
```

### 3. 管理者APIでAuth emailとprofiles.emailを同時更新する

管理者APIを使って、対象ユーザーのメールアドレスを修復する。

推定API：

```text
POST /api/admin-update-auth-email
```

認証・認可：

- 未ログインは401
- 一般ユーザーは403
- 管理者のみ実行可能
- `SUPABASE_SECRET_KEY` はサーバー側のみで使用
- ブラウザへsecret keyを出さない

リクエスト例：

```json
{
  "userId": "対象ユーザーID",
  "newEmail": "qtaro.dev.project1977+testuser2@gmail.com"
}
```

API側で行うこと：

```text
1. 管理者認証を確認
2. userId と newEmail を検証
3. newEmail が有効なメール形式か確認
4. Supabase Auth の対象ユーザー email を更新
5. profiles.email も同じ newEmail に更新
6. 必要であれば email_confirmed_at の扱いを確認
7. 成功時に管理者画面へ成功を返す
```

### 4. メール確認を要求するかどうかの方針

この機能は「管理者によるテストデータ修復」が主目的。

そのため、以下のどちらかを実装前に判断する。

#### 推奨A：管理者修復では即時反映

```text
管理者が指定したメールアドレスへ即時更新する
本人確認メールは送らない
```

用途：

```text
架空メールで作ったテストユーザーの修復
Auth email と profiles.email の整合回復
```

#### 代替B：管理者修復でも確認メールを送る

```text
管理者が新メールアドレスを設定
新メールへ確認メールを送る
確認完了後に反映
```

ただし、今回の問題は「現在メールが無効で本人フローが失敗する」ことなので、修復用途としてはAの即時反映が適している。

### 5. ログを残す

管理者がメール修復を行った記録を残す。

既存のログテーブルがあれば利用する。なければ、以下のような管理者監査ログを追加することを検討する。

テーブル案：

```text
admin_email_repair_logs
```

列案：

```sql
id uuid primary key default gen_random_uuid(),
target_user_id uuid not null references public.profiles(id) on delete cascade,
admin_user_id uuid not null references public.profiles(id) on delete cascade,
old_email text,
new_email text not null,
repaired_at timestamptz not null default now(),
reason text
```

ただし、既存に管理者操作ログが存在する場合は、新規テーブルを増やさず既存構造に合わせること。

初回実装でログ追加が大きすぎる場合は、最低限 `console.info` ではなくDB上の監査ログに残す設計を優先する。

### 6. 入力バリデーション

管理者修復UI/APIで以下を検証する。

OK例：

```text
qtaro.dev.project1977+testuser2@gmail.com
```

NG例：

```text
abc
abc@
@example.com
test
空欄
255文字以上
```

同じメールアドレスがすでに別ユーザーで使われている場合は、Supabase側のエラーを分かりやすく表示する。

表示例：

```text
このメールアドレスはすでに別ユーザーで使用されています。
```

### 7. 管理者画面の注意文

管理者ページには、通常のメール変更との違いを明記する。

文言例：

```text
この操作は、架空メールや不整合データを修復するための管理者専用操作です。
通常のメールアドレス変更は、ユーザー本人のユーザーデータ画面から行ってください。
```

### 8. 既存の「管理者ページではメール直接編集不可」方針との整合

チケット107では、管理者ページでメールを直接編集しない方針にしている。

ただし本チケットは、通常の編集機能ではなく、**壊れた既存テストユーザーを修復するための管理者専用救済機能**として扱う。

そのため、以下の制限を付ける。

- 管理者ページの通常保存ボタンではメールを変更できない
- メール修復は専用ボタンと確認モーダル経由のみ
- 実行前に対象ユーザーID・現在メール・修復後メールを表示する
- 誤操作防止の確認モーダルを必須にする

### 9. 確認モーダル

実行前に確認モーダルを表示する。

表示内容：

```text
管理者メール修復

対象ユーザー:
ユーザー名:
ユーザーID:
現在のメールアドレス:
修復後メールアドレス:

この操作はSupabase Auth email と profiles.email を同時に更新します。
実行してよろしいですか？
```

### 10. 成功時の表示

成功時は管理者画面に以下のようなメッセージを表示する。

```text
メールアドレスを修復しました。
ユーザー情報を再読み込みしてください。
```

可能であれば、修復後に管理者ユーザー一覧を自動再読込し、メール欄が新しいメールになっていることを確認できるようにする。

### 11. エラー表示

失敗時は、原因別に分かりやすく表示する。

例：

```text
管理者権限がありません。
メールアドレスの形式を確認してください。
このメールアドレスはすでに使用されています。
Supabase Auth email の更新に失敗しました。
profiles.email の更新に失敗しました。
```

内部エラー詳細は `console.error` やVercel Logsに出すが、secret keyやトークンは表示しない。

### 12. ドキュメント更新

以下を更新する。

- README
- 本番チェックリスト
- `docs/ticket_status.json`

`ticket_status.json` には `107fix4` を追加する。

Build番号も更新すること。

## 受け入れ条件（目視確認基準）

### 管理者UI表示

1. `AdminQtaro` でログインする
2. 管理者ページを開く
3. 架空メールのユーザーを選択する

例：

```text
testuser2 / test1@test.com
```

OK：

```text
管理者メール修復欄が表示される
現在メールアドレスが確認できる
修復後メールアドレスを入力できる
通常のユーザー情報保存とは別ボタンになっている
```

NG：

```text
通常のユーザー情報保存だけでメールが変えられる
一般ユーザーにも管理者メール修復欄が表示される
```

### 修復実行

1. 修復後メールアドレスに有効なGmailエイリアスを入力する

```text
qtaro.dev.project1977+testuser2@gmail.com
```

2. 管理者メール修復ボタンを押す
3. 確認モーダルを確認する
4. 実行する

OK：

```text
確認モーダルに対象ユーザー・現在メール・修復後メールが表示される
実行後に成功メッセージが表示される
```

NG：

```text
確認なしで即実行される
対象ユーザーが分からない
```

### Auth email / profiles.email の同期

修復後、管理者ページを再読み込みする。

OK：

```text
管理者ページのメール欄が新メールアドレスになる
ユーザーデータ画面の現在メールアドレスも新メールアドレスになる
```

NG：

```text
管理者ページだけ新メールになる
ユーザーデータ画面だけ新メールになる
Auth側とprofiles側がズレる
```

### 本人メール変更フローの再テスト

修復したユーザーでログインし、ユーザーデータ画面から別の有効メールアドレスへ変更申請する。

OK：

```text
メールアドレス変更確認メールが送信される
画面に成功メッセージが表示される
email_change_request_logs に1件追加される
```

NG：

```text
メールは届くが画面は失敗になる
email_change_request_logs が0件のまま
旧メールが無効というエラーが再発する
```

### 不正メール形式

管理者修復欄に以下を入力する。

```text
abc
abc@
@example.com
```

OK：

```text
メールアドレスの形式を確認してください。
Auth email / profiles.email は変更されない
```

### 重複メール

すでに別ユーザーで使用しているメールアドレスを入力する。

OK：

```text
このメールアドレスはすでに別ユーザーで使用されています。
```

NG：

```text
別ユーザーと同じメールアドレスが設定される
エラー内容が分からない
```

## 備考

このチケットは、本人による通常のメールアドレス変更申請機能を置き換えるものではない。

目的は、初期テスト時に架空メールで作成してしまった既存ユーザーや、Auth email / profiles.email の不整合があるユーザーを、管理者が安全に修復できるようにすること。

通常運用では、メールアドレス変更は引き続きユーザー本人のユーザーデータ画面から行う。
