# チケット31: クリアフラグ確認・削除用デバッグ機能とユーザーデータ削除機能

## 目的

パズルセレクト画面で、すでにクリア済み扱いになっている問題があり、サムネイルやクリア状態が表示されている。

開発中にクリアフラグが残ったままだと、動作確認や見た目確認がしにくいため、以下のどちらか、または両方を実装する。

```text
- クリアフラグあり / なし を確認できるデバッグ表示
- クリア状況やユーザーデータを削除できるデバッグ操作
```

最優先は、開発中に「クリア済み状態をリセットできる」こと。

## 対象ファイル（推定）

- `E:\Dev\web_picross_Ver2\js\state.js`
- `E:\Dev\web_picross_Ver2\js\actions.js`
- `E:\Dev\web_picross_Ver2\js\render.js`
- `E:\Dev\web_picross_Ver2\js\data.js`
- `E:\Dev\web_picross_Ver2\js\main.js`
- `E:\Dev\web_picross_Ver2\styles.css`

必要に応じて:

- `E:\Dev\web_picross_Ver2\users.json`
- `E:\Dev\web_picross_Ver2\server.js`

## 実装内容

### 1. クリア状況の保存場所を確認する

まず、現在のクリア済み状態がどこに保存されているか確認する。

確認候補:

```text
- localStorage
- sessionStorage
- state
- users.json
- サーバ側ユーザーファイル
- 問題データJSON内
```

確認すること:

```text
- どのキーで保存しているか
- ユーザー別に保存されているか
- 難易度別に保存されているか
- puzzle id / stageNo どちらで保存されているか
- サムネイル表示とクリアフラグが連動しているか
```

### 2. デバッグ用のクリアフラグ表示を追加する

開発中に確認しやすいように、パズルセレクト画面またはデバッグパネルに、クリア状態を確認できる表示を追加する。

表示候補:

```text
- クリア済み: あり / なし
- クリア数: 0 / 20
- 現在ユーザーのクリアデータ件数
- localStorageキー名
```

パズルパネル単位で表示する場合:

```text
#1 CLEAR
#2 未クリア
```

注意:

- 通常UIを邪魔しすぎない
- デバッグ表示は開発用として小さめにする
- 本番公開時に非表示にしやすい構造にする

### 3. クリア状況リセットボタンを追加する

現在ユーザーのクリア状況を削除できるボタンを追加する。

ボタン名候補:

```text
クリア状況リセット
クリアフラグ削除
進行状況を削除
```

期待動作:

```text
ボタン押下
→ 確認モーダル
→ OK
→ 現在ユーザーのクリアフラグを削除
→ パズルセレクトのクリア表示が消える
→ クリア数が 0 / n に戻る
```

注意:

- ブラウザ標準 `confirm()` ではなく、既存の画面内モーダルを使う
- クリア済み表示、CLEARバッジ、クリア数を更新する
- サムネイル自体は問題データ由来なら削除しない
- クリア済みで表示される特殊なサムネイルやバッジだけを解除する

### 4. ユーザーデータ削除ボタンを追加する

ユーザー単位の保存データを削除できるデバッグ操作を追加する。

ボタン名候補:

```text
ユーザーデータ削除
現在ユーザーのデータ削除
保存データ初期化
```

削除対象候補:

```text
- クリア状況
- プレイ履歴
- タイム記録
- ランキング用ローカルデータ
- エディタ以外のユーザー進行データ
```

注意:

- エディタの一時保存データまで削除するかは、別項目として分ける
- 誤操作防止の確認モーダルを必ず出す
- adminなど固定ユーザー自体を削除しない
- ログイン情報は削除対象に含めない方が安全

### 5. エディタ一時保存データとは分ける

今回の主対象は、ゲーム進行・クリア状態・ユーザー状態。

エディタの一時保存データは別管理とする。

```text
クリア状況リセット:
- ゲームクリアフラグのみ削除

ユーザーデータ削除:
- ユーザーのプレイ進行データを削除

エディタ一時保存削除:
- 既存の一時保存削除機能を使う
```

注意:

- エディタで作ったパズルデータや一時保存を勝手に削除しない
- 削除対象を画面に明記する

### 6. サーバ側ユーザーファイル保存と整合させる

チケット28でユーザーファイル保存が実装されている場合、クリア状況やユーザーデータ削除がサーバ側データにも反映されるようにする。

候補API:

```text
POST /api/user/clear-progress
POST /api/user/reset-data
GET /api/user/progress
```

ただし、静的版のみの場合はlocalStorage等を対象にする。

注意:

- サーバAPIが未実装の場合は、localStorage等のフロント側データ削除だけでよい
- サーバ保存がある場合は、READMEや最終報告に仕様を明記する

### 7. パズルセレクト画面を即時更新する

クリア状況を削除したら、ページ再読み込みなしでパズルセレクト画面の表示が更新されるようにする。

更新対象:

```text
- CLEARバッジ
- クリア数 0 / n
- クリア済みサムネイル表示
- デバッグ表示
```

注意:

- 問題そのものの完成サムネイルは、問題データ由来なら残す
- クリア済み専用表示だけを解除する

### 8. 誤操作防止を入れる

削除系操作は必ず確認を入れる。

確認モーダル例:

```text
クリア状況を削除しますか？

この操作で現在ユーザーのクリア状態がリセットされます。
パズルデータ自体は削除されません。

[キャンセル] [削除]
```

注意:

- ブラウザ標準 `confirm()` は使わない
- 既存テーマに合うモーダルを使う

## 受け入れ条件

- クリア状況の保存場所が確認されている
- クリアフラグあり / なし が開発中に確認できる
- クリア状況リセットボタンがある
- クリア状況リセット時に確認モーダルが出る
- クリア状況リセット後、CLEAR表示が消える
- クリア状況リセット後、クリア数が 0 / n に戻る
- クリア状況リセット後、同じ問題を再度プレイしてクリアできる
- ユーザーデータ削除ボタンがある
- ユーザーデータ削除時に確認モーダルが出る
- ユーザーデータ削除で固定ユーザー admin 自体は削除されない
- エディタの一時保存データを勝手に削除しない
- パズルデータJSON自体は削除しない
- パズルセレクト画面がページ再読み込みなしで更新される
- サーバユーザーファイルがある場合は、その仕様に合わせて削除処理が反映される
- 静的版の場合はlocalStorage等の保存データが削除される
- `node --check js/state.js` が通る
- `node --check js/actions.js` が通る
- `node --check js/render.js` が通る
- `node --check js/data.js` が通る
- サーバJSを変更した場合は `node --check server.js` が通る
- 変更したJSファイルすべてで `node --check` が通る
