# チケット134：ユーザー名ログイン用メール解決APIの秘匿化

## 目的

コードレビューで、未認証API `/api/resolve-login-email` がユーザー名から実メールアドレスを返しているため、ネットワークレスポンス経由でメールアドレス列挙に使える可能性が指摘された。

ログイン画面ではユーザー名＋パスワードの利便性を維持しつつ、ブラウザへ実メールアドレスを返さない、または最小限の情報だけ返す方式へ見直す。

## 対象ファイル（推定）

- `api/resolve-login-email.js`
- `js/supabaseAuth.js`
- `js/actions.js`
- `server.js`
- `js/config.js`
- `README.md`
- `docs/ticket_status.json`

## 実装内容

### 1. 現在のAPI挙動を確認する

- `/api/resolve-login-email` のレスポンス内容を確認する。
- 成功時に実メールアドレスを返しているか確認する。
- 失敗時のエラー文言でユーザー存在有無を漏らしていないか確認する。

### 2. メールアドレスをブラウザへ返さない方式を検討・実装する

- 可能であれば、ブラウザへ実メールアドレスを返さない設計に変更する。
- 候補：
  - サーバー側APIで `username + password` を受け、サーバー側でメール解決とログイン補助を行う
  - Supabase Auth制約上難しい場合は、レスポンスを最小化し、メール列挙リスクを下げる
- service_role keyをフロントエンドへ露出しない。

### 3. レート制限を追加する

- `/api/resolve-login-email` にレート制限を追加する。
- IP単位、ユーザー名単位、または既存ログテーブルを使った制限を検討する。
- 例：
  - 1時間に5回
  - 短時間連続失敗を拒否
- レート制限時は汎用エラーを表示する。

### 4. エラー表示を汎用化する

- 存在しないユーザー名、無効ユーザー、メール解決失敗などを過度に区別しない。
- 画面表示は以下のような汎用文言にする。
  - `ユーザー名またはパスワードを確認してください`
- ネットワークレスポンスでも、必要以上に詳細情報を返さない。

### 5. 既存ログイン体験を維持する

- ユーザー名＋パスワードだけでログインできる仕様を維持する。
- ユーザー登録、パスワード再設定、確認メール再送は既存仕様を維持する。
- 管理者ログインも維持する。

## 受け入れ条件（目視確認基準）

### メールアドレス非露出

- ブラウザの開発者ツールでログイン時の通信を見る。
- OK：レスポンスに実メールアドレスが出ない、または最小限に抑えられていること。
- NG：ユーザー名だけで実メールアドレスが取得できること。

### ログイン成功

- 既存ユーザーがユーザー名＋パスワードでログインする。
- OK：従来どおりログインできること。
- NG：メール非露出化によりログインできなくなること。

### ログイン失敗

- 存在しないユーザー名や誤ったパスワードを入力する。
- OK：汎用エラーが表示されること。
- NG：ユーザー名の存在有無が分かる詳細エラーになること。

### レート制限

- 短時間に複数回ログイン解決を試す。
- OK：一定回数以上で制限されること。
- NG：無制限にユーザー名列挙できること。
