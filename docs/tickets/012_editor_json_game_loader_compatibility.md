# チケット12: エディタ出力JSONとゲーム側読み込み形式の互換修正

## 目的

エディタで作成・出力したパズルデータを `data/beginner.json` などへ配置しても、ゲームセレクトから選択した際に「このパズルのデータがありません」と表示され、ゲーム側で認識されない問題を修正する。

原因として、エディタ出力JSONとゲーム側の読み込み期待形式に差異がある可能性が高い。

例:

```json
[
  {
    "id": "beginner_mono_id00000001",
    "stageNo": 1,
    "title": "クロス",
    "difficulty": "beginner",
    "mode": "mono",
    "colorMode": "mono",
    "w": 5,
    "h": 5,
    "grid": [
      ["1", "0", "0", "0", "1"],
      ["0", "1", "0", "1", "0"],
      ["0", "0", "1", "0", "0"],
      ["0", "1", "0", "1", "0"],
      ["1", "0", "0", "0", "1"]
    ],
    "grid_strings": [
      "10001",
      "01010",
      "00100",
      "01010",
      "10001"
    ]
  }
]
```

このようなエディタ出力形式でも、ゲーム側で正式な問題データとして扱えるようにする。

## 対象ファイル（推定）

- `E:\Dev\web_picross_Ver2\js\data.js`
- `E:\Dev\web_picross_Ver2\js\actions.js`
- `E:\Dev\web_picross_Ver2\js\render.js`
- `E:\Dev\web_picross_Ver2\js\state.js`
- `E:\Dev\web_picross_Ver2\js\engine.js`
- `E:\Dev\web_picross_Ver2\js\editor.js`
- `E:\Dev\web_picross_Ver2\data\*.json`

## 現象

ゲームセレクト画面で、エディタ作成済みの `beginner.json` を配置した状態でも、問題を選択すると以下のようなメッセージが出る。

```text
このパズルのデータがありません
```

## 想定原因

以下のような形式差異により、ゲーム側が対象パズルを見つけられていない可能性がある。

```text
- ゲーム側が id = 1 のような数値IDを期待している
- エディタ出力側は id = beginner_mono_id00000001 のような文字列IDになっている
- ゲーム側が配列インデックスや puzzle.id で探している
- エディタ出力側は stageNo = 1 を持っている
- ゲーム側が width / height を期待している
- エディタ出力側は w / h を持っている
- ゲーム側が solution / cells を期待している
- エディタ出力側は grid / grid_strings を持っている
```

## 実装内容

### 1. ゲーム側の問題検索処理を確認する

まず、ゲームセレクトから問題を選択したときに、どの値で問題を探しているか確認する。

確認対象候補:

```text
- actions.play()
- loadPuzzles()
- getPack()
- renderSelect()
- state.currentPuzzle
```

確認すること:

```text
- 問題番号 #1 を押したとき、何をキーに探しているか
- id を数値として見ているか
- stageNo を見ているか
- 配列のindexを見ているか
- difficulty を照合しているか
```

### 2. stageNo で問題を探せるようにする

エディタ出力JSONに `stageNo` がある場合、ゲーム側は `stageNo` を問題番号として扱えるようにする。

期待動作:

```text
#1 を選択
→ stageNo: 1 のパズルを探す
→ 見つかったらそのパズルを読み込む
```

注意:

- 既存の `id` 検索がある場合は壊さない
- `id` と `stageNo` の両方がある場合は、既存仕様と矛盾しない優先順位を決める
- `stageNo` は数値・文字列どちらでも安全に比較できるようにする

### 3. 文字列IDにも対応する

エディタ出力では、以下のような文字列IDが使われる可能性がある。

```text
beginner_mono_id00000001
```

このような文字列IDでも、問題データとして無効扱いしないようにする。

注意:

- IDを数値変換して `NaN` になった場合に失敗しないようにする
- `stageNo` がある場合は `stageNo` を表示番号として使えるようにする
- `id` は内部識別子として保持してよい

### 4. w / h と width / height の表記ゆれを吸収する

読み込み時に、以下のどちらでも盤面サイズを取得できるようにする。

```text
w / h
width / height
```

期待動作:

```text
w: 5, h: 5
→ width: 5, height: 5 と同等に扱う
```

注意:

- 保存・出力時は既存方針に合わせて統一してよい
- 読み込み時は互換性を優先する

### 5. grid / grid_strings から盤面を復元できるようにする

エディタ出力形式では、盤面データとして以下を持つ可能性がある。

```text
grid
grid_strings
```

どちらからでも正解盤面を復元できるようにする。

優先順位候補:

```text
1. grid が有効なら grid を使う
2. grid がない場合、grid_strings から復元する
3. 既存形式の solution / cells がある場合は既存処理を維持する
```

注意:

- モノクロ問題では `"1"` を塗り、`"0"` を空白として扱う
- カラー問題では `0`〜`9` / `A`〜`F` のカラーIDを保持できるようにする
- 空白や未入力の扱いを既存仕様に合わせる
- 小文字 `a`〜`f` が来た場合は大文字へ正規化する

### 6. 既存JSON形式とエディタ出力JSON形式の両方を読み込めるようにする

既存の `data/*.json` 形式を壊さず、エディタ出力形式も読み込める互換レイヤーを作る。

実装候補:

```text
normalizePuzzle(rawPuzzle, context)
normalizePuzzles(rawJson, context)
```

正規化後の内部形式は、既存のゲーム処理が扱いやすい形に統一する。

注意:

- 生データを直接あちこちで判定しない
- 読み込み時に一度正規化し、以後は統一形式で扱う
- 既存の通常問題データも正規化後に壊れないようにする

### 7. 「このパズルのデータがありません」の原因をログに出す

問題が見つからなかった場合、開発時に原因を追いやすいように `console.warn` などで情報を出す。

出力候補:

```text
- 選択されたdifficulty
- 選択された問題番号
- 読み込んだJSONの件数
- 各パズルのid / stageNo
- どの条件で一致しなかったか
```

注意:

- ユーザー向け表示は簡潔でよい
- consoleには開発者向け情報を出す
- 本番でも致命的な情報漏洩にならない範囲にする

### 8. エディタ出力側も必要なら軽く調整する

読み込み側の互換修正を優先する。  
ただし、エディタ出力側で明らかに不足している項目がある場合は、既存互換を壊さない範囲で補う。

候補:

```text
- stageNo
- id
- difficulty
- mode / colorMode
- w / h
- width / height
- grid
- grid_strings
```

注意:

- 出力形式を大きく変えるより、読み込み側で吸収することを優先する
- 既に出力済みのJSONも読めるようにする

### 9. 通常問題とエディタ作成問題の両方を確認する

以下の両方で動作確認する。

```text
- 既存のdata/*.json
- エディタで作成・出力したdata/*.json
```

特に `beginner.json` を差し替えた場合でも、ゲームセレクトの `#1` から問題が開始できることを確認する。

- カラー問題で `0`〜`9` / `A`〜`F` のカラーIDが正しく扱われる
