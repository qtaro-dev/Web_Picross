# チケット120：ログイン時のメールアドレス入力不要化

## 目的

現在のログイン画面では、ログイン時にもメールアドレス入力が必要に見えるため、毎回のログイン操作が手間になっている。

ログイン時は「ユーザー名」と「パスワード」のみでログインできるようにし、メールアドレス入力はユーザー登録・パスワード再設定・確認メール再送など、必要な場面だけに限定する。

## 対象ファイル（推定）

- `index.html`
- `styles.css`
- `js/supabaseAuth.js`
- `js/actions.js`
- `js/render.js`
- `js/state.js`
- `js/config.js`
- `api/user-reset-password.js`
- `api/user-resend-confirmation.js`
- `api/resolve-login-email.js`（新規追加候補）
- `README.md`
- `docs/ticket_status.json`

## 実装内容

### 1. ログインフォームの入力項目を整理する

- ログイン時は以下のみ入力するUIに変更する。
  - ユーザー名
  - パスワード
- ログイン操作では、メールアドレス欄を必須にしない。
- ログインボタン押下時に、メールアドレス未入力を理由にログイン失敗扱いにしない。
- 既存の「メールアドレスとパスワードを記録する」相当の表示がある場合は、ログイン時の新仕様に合わせて文言・保存対象を見直す。
- 既存テーマ・背景・ボタンデザインは維持する。

### 2. 内部的にはユーザー名からメールアドレスを解決してログインする

- Supabase Auth はメールアドレス + パスワード認証が基本のため、画面上はユーザー名ログインにしつつ、内部ではユーザー名からメールアドレスを取得してログインする。
- ログイン時の想定処理：
  1. 入力されたユーザー名を検証する。
  2. ユーザー名に対応するメールアドレスを取得する。
  3. 取得したメールアドレスと入力パスワードで Supabase Auth ログインを行う。
- ユーザー名からメールアドレスを解決する処理は、安全な方法で実装する。
- クライアント側から不要に全ユーザーのメールアドレスを取得できるようにしない。
- RLSや既存のセキュリティ方針を破壊しない。
- 必要であれば、専用APIを追加する。
  - 例：`api/resolve-login-email.js`
- APIを追加する場合、過度な情報漏えいを避ける。
  - 存在しないユーザー名の場合も、エラーメッセージで過剰に情報を出さない。
  - レスポンスはログイン処理に必要な最小限にする。
- 既存のprofiles構造・Supabase Auth構造を壊さない。

### 3. ユーザー登録時はメールアドレス必須のまま維持する

- ユーザー登録では、引き続き以下を入力する。
  - ユーザー名
  - パスワード
  - メールアドレス
- 登録時のメール確認フローは維持する。
- 登録時のメールアドレス形式チェックは維持する。
- 登録時のメールアドレス文字数制限は既存仕様を維持する。
- 登録処理では、メールアドレス未入力なら登録できないようにする。

### 4. パスワードを忘れた場合のメール入力UIを分離する

- 「パスワードを忘れた場合」を押したときだけ、メールアドレス入力UIを表示する。
- 表示方式は以下のいずれかとする。
  - モーダル
  - 折りたたみフォーム
  - 専用の小フォーム
- 入力項目：
  - メールアドレス
- ボタン例：
  - `再設定メールを送信`
- この処理ではメールアドレス入力を必須にする。
- 既存のパスワード再設定メール送信処理を維持する。
- 既存の回数制限・ログ保存・redirectTo設定がある場合は維持する。

### 5. 確認メール再送のメール入力UIを分離する

- 「確認メールを再送する」を押したときだけ、メールアドレス入力UIを表示する。
- 表示方式は以下のいずれかとする。
  - モーダル
  - 折りたたみフォーム
  - 専用の小フォーム
- 入力項目：
  - メールアドレス
- ボタン例：
  - `確認メールを再送`
- この処理ではメールアドレス入力を必須にする。
- 既存の確認メール再送処理を維持する。
- 既存の回数制限・ログ保存・redirectTo設定がある場合は維持する。

### 6. 画面上の文言を用途別に整理する

- ログイン画面で、ログイン時にメールアドレスが不要であることが自然に分かる表示にする。
- 例：
  - ログイン：ユーザー名とパスワードを入力してください
  - ユーザー登録：ユーザー名・パスワード・メールアドレスを入力してください
  - パスワード再設定：登録済みメールアドレスを入力してください
  - 確認メール再送：登録済みメールアドレスを入力してください
- 既存の日本語UIトーンを維持する。
- ハードコード文字列は禁止。既存の文言管理方針がある場合はそれに従う。

### 7. 既存機能を壊さない

- 既存のログイン成功後の遷移を維持する。
- 管理者ログイン時の管理者判定を維持する。
- 一般ユーザーのログインを維持する。
- ユーザー登録処理を維持する。
- パスワード再設定処理を維持する。
- 確認メール再送処理を維持する。
- メールアドレス変更処理、管理者メール修復処理には影響を出さない。
- 既存テーマ・ライブラリ構成を維持する。
- ICommand構造を崩さない。

## 受け入れ条件（目視確認基準）

### ログイン：メールアドレスなし

- ユーザーがログイン画面を開く。
- ユーザーがユーザー名とパスワードを入力する。
- ユーザーはメールアドレスを入力しない。
- ユーザーがログインボタンを押す。
- OK：正しいユーザー名とパスワードならログインできること。
- NG：メールアドレス未入力を理由にログインできないこと。

### ログイン：誤ったユーザー名

- ユーザーが存在しないユーザー名を入力する。
- ユーザーが任意のパスワードを入力する。
- ユーザーがログインボタンを押す。
- OK：ログイン失敗として扱われること。
- OK：過剰に「このユーザー名は存在します / 存在しません」などの情報を出しすぎないこと。
- NG：内部エラー表示や白画面になること。

### ログイン：誤ったパスワード

- ユーザーが正しいユーザー名を入力する。
- ユーザーが誤ったパスワードを入力する。
- ユーザーがログインボタンを押す。
- OK：ログイン失敗として扱われること。
- NG：別ユーザーとしてログインすること。

### 管理者ログイン

- 管理者ユーザーがユーザー名とパスワードのみでログインする。
- OK：ログイン後に管理者権限が従来どおり反映されること。
- OK：管理者ページへ入れること。
- NG：管理者判定が外れること。

### ユーザー登録

- 新規ユーザーがユーザー登録を行う。
- ユーザー名、パスワード、メールアドレスを入力する。
- OK：メールアドレス入力欄が登録時には表示されること。
- OK：メールアドレス未入力では登録できないこと。
- OK：登録確認メールの既存フローが維持されること。
- NG：ログイン用UI変更の影響で登録できなくなること。

### パスワードを忘れた場合

- ユーザーが「パスワードを忘れた場合」を押す。
- OK：メールアドレス入力UIが表示されること。
- ユーザーが登録済みメールアドレスを入力する。
- ユーザーが再設定メール送信ボタンを押す。
- OK：既存のパスワード再設定メール送信処理が動くこと。
- NG：ログインフォームのメールアドレス欄がないために再設定処理が使えなくなること。

### 確認メール再送

- ユーザーが「確認メールを再送する」を押す。
- OK：メールアドレス入力UIが表示されること。
- ユーザーが登録済みメールアドレスを入力する。
- ユーザーが確認メール再送ボタンを押す。
- OK：既存の確認メール再送処理が動くこと。
- NG：ログインフォームのメールアドレス欄がないために再送処理が使えなくなること。

### 保存チェック

- ユーザーがログイン情報保存チェックを使う。
- OK：新仕様に合わせて保存対象が自然であること。
- OK：再訪問時にログインしやすくなっていること。
- NG：メールアドレス欄がないのに古いメールアドレス保存UIだけが残ること。

### 回帰確認

- ユーザーが通常プレイ画面へ進む。
- OK：ログイン後にゲーム選択・実プレイ・エディタ・ユーザーデータ画面へ従来どおり移動できること。
- 管理者が管理者ページを開く。
- OK：ユーザー管理、進行状況、ランキング、パズル管理などが従来どおり使えること。
